# Authentication Implementation Findings

Date: November 4, 2026. **Status: implemented, partially verified; not complete.** The native denied-authentication alert remains failing. Changes stopped under the AGENTS.md circuit breaker after two consecutive failures of that assertion with the presentation cause unresolved.

## Implemented Boundary

- Normal Debug and Release use `LAContext.evaluatePolicy(.deviceOwnerAuthentication)` with an explanatory Face ID purpose string. The system owns biometrics and device-passcode fallback; the app stores no PIN or biometric data.
- The store starts locked. A locked reload exposes aggregate soldier/result counts only. Names, photos, notes, measurements, certificates, saved-result details, and all tabs remain behind authentication. Restored tab/record selection cannot open the protected UI before unlock.
- Record access, attachment URLs/bytes, edits, saves, deletes, draft updates, and explicit recovery check the authenticated store boundary. Actor-queued writes and attachment reads additionally check a revocable lease. Work already admitted to an atomic transaction can finish; stale results cannot republish after locking.
- Authentication requests have identities; cancellation/relocking invalidates them. A late successful callback cannot unlock a later session. Errors retain underlying diagnostics while exposing sanitized messages.
- Background/device-lock notifications and manual lock clear the public detail state and draft, cancel owned work, and revoke the lease. All windows share the session. Unsaved editor state is discarded when protected views are removed; already committed data is retained.
- A window-level opaque privacy cover is intended to sit above sheets/Quick Look while inactive; lock transitions also dismiss presentations. The summary is explicitly nonsensitive. Authentication's temporary inactive state does not itself revoke the request.

## Test Configuration and Remaining Limits

A separate **Testing** build configuration substitutes only the external OS authentication provider. The real store, repository, filesystem, lock/revocation state, and UI remain under test. It is not a test bypass compiled into normal Debug or Release. Do not distribute Testing builds. The normal run/archive configurations remain Debug/Release respectively. The public OS policy call compiles, but a successful simulator test-double unlock is not evidence of a successful real biometric/passcode challenge.

Locked summary generation still loads data into the private repository and can perform existing journal recovery. This is an app-service access boundary, not a cryptographic vault or a guarantee that all decrypted bytes are erased from memory. Previously returned values cannot be retroactively revoked; protected UI is removed and future service calls are blocked. Backup/sharing policy and actual hardware capture/lock behavior remain open from the privacy audit.
